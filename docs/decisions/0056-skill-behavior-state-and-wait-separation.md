# 0056 - 技能行为树分离状态声明与生命周期等待

- **状态**: Accepted
- **日期**: 2026-08-22
- **决策层**: 编排层 / 跨层（引擎与渲染）
- **相关代码**: `src/engine/core/World/Member/`、`db/scripts/importToramSkillBehaviors.mjs`、`src/components/tools/BtEditor/data/SkillExamples.ts`
- **相关 ADR**: Refines 0053

## 决策问题

技能行为树需要表达成员进入某个逻辑动作状态，并在该状态期间阻止流程继续推进。需要决定状态声明是否同时拥有生命周期时长，还是将状态语义与行为树等待语义分开，以保持技能流程的可组合性和引擎与渲染层的职责边界。

## 决策驱动

- 逻辑状态是引擎输出的语义事实，不应携带动画资源、播放策略或表现时长。
- 技能阶段既可能按生命周期时长推进，也可能由攻击节点、子树结果、条件或中断决定完成。
- 行为树需要复用等待、循环、分支和中断等通用控制流，而不应为技能阶段复制专用计时器。
- 成员 FSM 是生命周期和互斥的权威，active effect BT 只能在其允许的范围内细化动作状态。

## 候选方案

### A. 状态声明同时负责等待

使用一个携带状态和时长的专用原语，原语完成时推进到下一个流程节点。

- 优点：技能数据的表面节点数量较少，固定时长阶段的书写较短。
- 缺点：把状态事实、行为树控制流和计时生命周期绑定；难以表达由子树、事件或中断决定结束的状态；还会复制通用等待原语的计时、中断和恢复语义。

### B. 状态声明与等待分离

使用瞬时状态声明原语表达当前逻辑状态，使用独立等待原语控制行为树何时继续。

- 优点：状态生命周期由行为流程和成员生命周期共同决定；等待可以独立用于固定时长、动态时长和其他控制流；状态声明不需要理解渲染资源或计时细节。
- 缺点：固定时长阶段需要显式书写两个原语；技能导入器和作者需要遵守状态声明与等待的组合约定。

## 决议

选择 B：**技能行为树使用独立的状态声明原语和通用等待原语；状态声明不携带生命周期时长，也不负责动画播放。**

确立以下不变量：

1. 状态声明只提交稳定的逻辑状态语义，并记录状态进入的逻辑时间边界。
2. 等待原语只负责行为树控制流的时间推进；它可以与状态声明组合，也可以单独使用。
3. 状态持续到下一次状态声明、行为流程结束或成员生命周期中断；状态声明本身不维护独立的完成计时器。
4. FSM 继续拥有成员生命周期、互斥和中断权威；active effect BT 只能在技能执行期间声明动作状态。
5. 渲染层根据逻辑状态、逻辑时间和本地资源映射计算动画表现，逻辑引擎不输出动画片段、播放倍率或渲染完成事件。
6. 不建立携带动画资源或状态时长的第二套状态原语；需要更短的作者语法时，只能在编译阶段展开为上述两个独立语义。

## 代价

- 固定时长的技能阶段需要显式表达状态声明和等待，行为树数据会更强调控制流结构。
- 技能导入器、编辑器示例和既有行为数据必须共同遵守同一组合约定。
- 渲染资源仍需维护逻辑状态到本地表现的映射；逻辑生命周期时长与本地动画片段时长可以不同，表现层自行处理差异。

## 重新评估条件

- 技能状态必须由渲染资源的播放完成事件反向决定逻辑流程完成。
- 同一成员需要同时维护多个独立动作状态层，并且单一状态汇合规则无法表达冲突。
- 大量状态无法由行为流程、事件或成员生命周期决定结束，且已测量出独立等待原语造成明显的性能或可维护性问题。
- 状态需要跨进程或持久化传递精确的结束时间，而当前逻辑状态与本地表现映射无法满足该契约。
